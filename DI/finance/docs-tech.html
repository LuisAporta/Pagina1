Inmersión Técnica y Programación

Guía exhaustiva del funcionamiento interno del sistema

1. El Ciclo de Conexión (El Cliente SDK)

La aplicación utiliza el SDK oficial de **Supabase JS** para desacoplar el frontend del backend tradicional. La conexión no es persistente (no hay WebSockets abiertos en todo momento), sino que funciona mediante llamadas REST autenticadas sobre HTTP/2.

js/common.js - Inicialización
// Se verifica la existencia de la librería y las constantes globales
if (typeof supabase !== 'undefined' && typeof CONFIG !== 'undefined') {
    // Inicialización del cliente singleton utilizando el patrón factory
    window.sbClient = supabase.createClient(
        CONFIG.SUPABASE_URL,       // Endpoint de la REST API
        CONFIG.SUPABASE_ANON_KEY   // Clave pública para el sistema Auth
    );
}

Por qué funciona así: Al usar window.sbClient, permitimos que cualquier página de la aplicación (Dashboard, Transacciones, etc.) acceda al mismo objeto de conexión sin tener que re-autenticar al usuario ni volver a instanciar el cliente.

2. Manipulación de Datos y Consultas

Las llamadas a la base de datos se realizan mediante una interfaz fluida (Fluent Interface) que traduce el código JavaScript directamente a sentencias PostgREST en el servidor.

dashboard.html - Lectura de Datos
// Ejemplo de consulta asíncrona filtrada por usuario
const { data, error } = await window.sbClient
    .from('transactions') // Tabla principal
    .select('*')          // Traemos todas las columnas
    .eq('user_id', user.id); // Cláusula WHERE de seguridad
transactions.html - Inserción Segura
// El proceso de guardado incluye la vinculación automática del ID de sesión
const txObj = {
    amount: parseFloat(amt),
    type: currentType, // 'income' | 'expense'
    user_id: user.id   // El user.id proviene de localStorage.finance_session
};

const { error } = await window.sbClient
    .from('transactions')
    .insert([txObj]);

Seguridad RLS: Aunque el código parece "abierto", Supabase bloquea cualquier petición que no cumpla las **Row Level Security Policies**. El user_id debe coincidir con el token JWT de la sesión, o la DB devolverá un error 403 automáticamente.

3. Inteligencia en el Servidor (SQL Triggers)

Para evitar desincronizaciones en el saldo, no calculamos el "Líquido" en el cliente. Usamos lógica procedimental en el servidor (**PL/pgSQL**) que se activa ante cualquier cambio.

db_setup.sql - Lógica Procedimental 
-- Esta función se ejecuta en el SEGUNDO en que haces un INSERT o DELETE
create or replace function update_total_balance()
returns trigger as $$
begin
  update profiles
  set total_balance = (
    select coalesce(sum(case when type = 'income' then amount else -amount end), 0)
    from transactions
    where user_id = coalesce(new.user_id, old.user_id)
  )
  where id = coalesce(new.user_id, old.user_id);
  return null;
end;
$$ language plpgsql;

El Disparador (Trigger): Hemos configurado el trigger on_transaction_change para que escuche los eventos AFTER INSERT OR UPDATE OR DELETE. Esto significa que el código de la app solo inserta una transacción, y la base de datos "mágicamente" actualiza el saldo global antes de que el dashboard se refresque.

4. Gestión Estructurada de Archivos

Los archivos (comprobantes) no se guardan como BLOBs en la base de datos, sino como objetos en un Storage Bucket optimizado.

Lógica de Carga de Recibos
// 1. Fase de Validación Local
const file = fileInput.files[0];
const fileExt = file.name.split('.').pop();
const fileName = `${Math.random()}.${fileExt}`;

// 2. Fase de Carga Remota
const { data, error } = await window.sbClient.storage
    .from('receipts') // Bucket destino
    .upload(`${user.id}/${fileName}`, file); // Carpeta privada por usuario

Este flujo es eficiente porque la aplicación solo almacena la **URL** del archivo en la tabla de transacciones, mientras que el binario pesado reside en los servidores de almacenamiento optimizados de Supabase.
