1. Arquitectura & Flujo de Datos

El sistema se fundamenta en un modelo Cliente-Servidor asíncrono diseñado para superar las limitaciones de seguridad de los navegadores modernos ("Sandboxing"). Un navegador web estándar no tiene permisos para leer la memoria RAM del sistema ni ejecutar procesos; por ello, delegamos esa responsabilidad a un entorno de ejecución local (Node.js).

[ FRONTEND (Cliente) ]
HTML5 / CSS3 / Vanilla JS / Chart.js

⬇️ Solicitud HTTP (JSON) via Fetch API ⬆️

[ BACKEND (Servidor) ]
Node.js / Express / Child_Process

⬇️ Ejecución de Comandos del Sistema (Shell) ⬆️

[ KERNEL (Sistema Operativo) ]
Windows Management Instrumentation (WMIC)

2. Análisis Profundo del Código

A continuación, desglosamos los módulos críticos que componen la lógica de negocio de la aplicación.

A. BACKEND: La API de Control (`server.js`)

El backend utiliza el framework Express para levantar un servidor web ligero. Su función principal es exponer "Endpoints" (puntos de acceso) que el frontend puede llamar.

Punto Clave: Interacción con el Sistema
Utilizamos la librería nativa child_process. Esto nos permite abrir una terminal "invisible" en el servidor, escribir un comando como si fuéramos un usuario (ej: wmic para Windows o free -m para Linux), y capturar el texto que devuelve.

B. FRONTEND: Lógica de Visualización (`app.js`)

El frontend se encarga de la experiencia de usuario. Sigue una lógica de "Polling" (sundeo): cada X segundos, pregunta al servidor "¿Cómo estás?" y actualiza la pantalla.

Punto Clave: Modo Simulación (Fallo Seguro)
Dado que GitHub Pages solo aloja archivos estáticos (HTML/CSS/JS) y no puede ejecutar Node.js, implementamos una lógica de "Fallback". Si el frontend detecta que el servidor no responde (fetch falla), activa automáticamente un Modo Simulación para no romper la experiencia visual.

C. ESTILO: Arquitectura CSS (`style.css`)

Para conseguir el efecto "Cyberpunk", no usamos librerías como Bootstrap. Todo es CSS Nativo utilizando:

  • Variables CSS (`:root`): Centralizan los colores neón (`--neon-blue`, `--neon-purple`) para cambios globales rápidos de tema.
  • Glassmorphism: Uso de fondos semitransparentes (`rgba(0,0,0,0.8)`) para superponer paneles sobre el fondo animado.
  • CSS Grid Layout: Define la estructura rígida del dashboard (Columnas 1fr 2fr) manteniéndolo responsivo.
  • Animaciones Keyframes: Para el latido del núcleo rojo (`pulse-red`) y el brillo de los botones.

3. Proceso de Resolución del Proyecto

Metodología de desarrollo incremental utilizada para construir la aplicación, desde el concepto básico hasta el producto final pulido.

FASE 1: Prototipado "Backend First"

Node.js Express MVP

El primer desafío fue establecer la comunicación técnica. No importaba el diseño, solo que Node.js pudiera hablar con el Sistema Operativo.

PROMPT INICIAL: "Crea una carpeta dashboard-servidores. Inicializa Node.js e instala express. REGLAS: Sin tildes en código, Javascript Vanilla, semáforo visual y ejecución de comandos reales."

Resultado: Un servidor funcional pero con una interfaz HTML blanca muy básica. Se verificó que `exec` funcionaba correctamente en Windows.

FASE 2: Integración y Despliegue

Git GitHub Refactor

Se procedió a organizar el código en una estructura profesional (`ASI/` y `DI/`) y subirlo a la nube. Surgieron conflictos de nombres de archivo (`ejercicio.html` vs `index.html`) que requirieron intervención manual en Git.

ACCIÓN CLAVE: Resolución de conflictos de "Merge" en Git, eliminando archivos duplicados y unificando la navegación.

FASE 3: Rediseño Visual Total ("Overhaul")

CSS3 Cyberpunk Chart.js

El usuario rechazó el diseño inicial por ser "cutre". Se iteró hacia una estética agresiva inspirada en "Tokyo Night". Se abandonó el diseño plano por uno con profundidad (sombras, neones).

FEEDBACK USUARIO: "No me gusta nada el estilo, es muy feo. Quiero una estética gótica cyberpunk neon street japonesa, super estética. Pon fotos de fondo y hazlo atractivo."

Solución: Se reescribió el 100% del CSS. Se añadieron fuentes de Google (Orbitron) y se integró Chart.js para visualización de datos en tiempo real, reemplazando las listas de texto plano.

FASE 4: Documentación y Estabilización

Docs Debugging Inyección CSS

Al desplegar en GitHub Pages (entorno estático), el dashboard falló visualmente. Se diagnosticó un problema de caché y de carga de CSS externo.

SOLUCIÓN TÉCNICA: Se inyectó el CSS crítico ("Critical Path CSS") directamente en el HTML y se programó el "Modo Simulación" en Javascript para que la web no parezca rota si no hay conexión con el backend.
